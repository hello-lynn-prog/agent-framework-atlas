展开：三类事件各走哪条路
  1. 助手文本/推理 delta → 流式上屏 + 记录（plan 模式有专门的分段状态机 AssistantMessageStreamParsers）。
  2. OutputItemDone：工具调用（FunctionCall / LocalShellCall / WebSearchCall / MCP…）→ 塞进 FuturesOrdered in_flight 并发执行（见右侧"工具调用的一生"），不等前一个跑完。
  3. OutputItemDone：最终消息 → 记 last_agent_message；response.completed → 内层循环正常结束。
▼ 内层循环结束，带着 needs_follow_up 和 last_agent_message 回到外层
D · 采样后体检 context_window_token_status · turn.rs:558 起
回收异步钩子结果 → 查 token 占用 → needs_follow_up = 模型要继续(有工具调用) || 有用户插话。
D1 · 顶到上下文上限 → 压缩后换新窗口继续
  • run_auto_compact (1471)，phase=MidTurn
  • 摘要换掉旧历史 → 新 context window
  • continue → 回到 A
  • 压缩失败 → 发错误事件，turn 结束
D2 · needs_follow_up=true → 继续
  • 工具结果已在历史里
  • continue → 回到 A，开始下一个 step
  • 这就是"agent loop"的循环体：模型→工具→模型→…
D3 · 模型给最终答案了 → 收尾三连
  • Stop 钩子 run_turn_stop_hooks：可以"打回"——注入 hook 提示词强制再跑一步（防过早收工）
  • legacy after_agent 钩子
  • 轮末压缩：超过阈值且无插话 → run_auto_compact，phase=PostTurn
  • break → 返回 last_agent_message
错误出口（match Err 分支）
  • ContextWindowExceeded（guardian 场景）→ 压缩重试一次
  • TurnAborted（用户 ESC）→ 直接返回
  • 图片不合法 → 提示用户删图重试
  • 其它 → emit_turn_error_lifecycle + Error 事件 → break（会话保留，可继续聊）
▲ continue 回到循环头（A）　｜　break 出循环 → turn 结束，返回 last_agent_message

🔧 工具调用的一生（C3 分出的支线）

  • 并发池：ToolCallRuntime tools/parallel.rs:45，调用进 FuturesOrdered，完成顺序回填历史
  • 编排：ToolOrchestrator.run tools/orchestrator.rs:125（带重试的 run_attempt）
  • 路由：dispatch_tool_call tools/router.rs:304 — 按 ToolName 找 CoreToolRuntime（内置 shell / apply_patch / unified_exec / MCP / 多代理 / plan / view_image…tools/handlers/）
  • 审批：request_approval tools/approvals.rs:479 — 三级：用户(679) / guardian(572) / reviewer(554)；发 EventMsg::ExecApprovalRequest 等 ReviewDecision（approve / deny / 防护四态在 protocol/approvals.rs）
  • 执行：core/tools/sandboxing.rs 选沙箱 → linux-sandbox / windows-sandbox / network-proxy 真跑命令
  • 回填：function_call_output 记进 history + rollout → 下一次 build_prompt 时缝合进 prompt（C1 的 attach_to_prompt）

📦 压缩（compact）的三个时机

  • PreTurn：进循环前（run_pre_sampling_compact，1298）
  • MidTurn：step 之间顶到上限（run_auto_compact，1471）
  • PostTurn：答完之后闲时整理（阈值百分比可配）
  • 远端压缩（V2）走 provider 能力协商；本地失败有 model fallback（compact_model_fallback.rs）

🔌 钩子在循环上的五个位置

  • ① session_start（回合开始补跑）
  • ② user prompt 落历史时（run_hooks_and_record_inputs，866 — 可拦截输入）
  • ③ 异步钩子结果回收（drain_async_hook_results，采样前后各一次）
  • ④ Stop 钩子（可打回收尾，强制继续 — 和 Claude Code 的 Stop hook 同思路）
  • ⑤ legacy after_agent（旧通知机制兜底）
  • 对照 deepagents：deepagents 是中间件"包裹"整个调用；codex 是循环体内固定插座，循环本身不可包裹（六方对比里 codex 的"边缘插入"）

📝 全程伴跑的两条旁路

  • 持久化：所有 record_* 同时写 rollout（JSONL，rollout/ crate）+ SQLite 元数据（state/）→ resume/fork 的数据源
  • 事件流：所有 send_event 发 EventMsg（protocol/ 定义）→ channel → 三个壳各自渲染；审批请求也走这条路上浮给用户

一句话总结：codex 的 agent loop 是两层循环——外层 step 循环管"继续还是收工"（插话、压缩、Stop 钩子都在这层决策）， 内层采样循环管"一次模型往返"（流式收事件、并发跑工具、失败重试）。两层都能被 CancellationToken 从外部整个斩断。
